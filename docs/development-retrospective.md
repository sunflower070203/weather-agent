# 从 API 问答到可测试 Agent：开发复盘

## 起点

项目最容易走向一条熟悉路线：接入天气 API，再让模型把返回值改写成建议。这个方案能做出页面，却没有解决 Agent 开发中困难的部分——状态如何保存、何时追问、工具失败后怎么办、结论能否稳定复现。

提交版把目标收缩为可验证的循环：用户描述户外计划，系统补齐必要条件，查询真实天气，按照公开规则识别风险，给出主方案和备选方案；用户修改时间或地点后，系统保留仍有效的信息并重新评估。

## 四个关键取舍

第一，先做单 Agent。多 Agent 会增加通信、状态同步和调试成本，当前任务没有需要多个角色协作的硬需求。显式状态机加少量模型能力已经能覆盖目标。

第二，天气事实和风险判断不交给模型自由生成。模型负责理解口语与组织说明，API 提供天气事实，Python 规则计算风险。这样才能对同一组数值给出稳定结论，也能写出有意义的测试。

第三，保留地点歧义。地理编码返回多个候选时，让用户确认可以避免把错误坐标包装成精确建议。对于部分具体地点，系统会明确标注城市级近似。

第四，把失败路径当成产品行为。过去日期、非法时长、预报越界、模型异常和天气服务失败都应该得到明确响应。安全停止比生成没有数据依据的建议更重要。

## 测试如何改变设计

测试覆盖了候选地点选择、中文序数词、计划修改、提示注入字段、预报越界、服务失败、会话重置和 UI 状态隔离。对抗测试暴露了三个具体问题：候选阶段修改计划可能被误当成候选选择，超长活动可能在校验前进入工具链，标准直辖市名可能产生无意义候选。修复后，完整测试集达到 60 项。

页面可打开不等于 Agent 已经跑通。线上验收必须从新会话完成一次评估，再修改计划触发重评估，并验证错误输入不会得到伪造结论。提交候选版加入可见版本标识，用来解决“仓库已经更新，线上是否真在运行同一版本”这个部署盲点。

## 当前结论

项目形成了受控的 Agent 技术闭环，同时仍有清楚的边界。它没有路线级气象能力、长期记忆、知识库或多 Agent 协作。下一步先完成版本一致的线上发布和固定回归；提交后再按“可测的 Skill 工具边界、评测集扩充、可追溯记忆、最后才是多 Agent”的顺序学习扩展。

可复用流程是：先定义决策任务与失败条件，再建模状态和工具契约，使用确定性程序守住事实边界，以对抗场景驱动修复，最后用可见版本和线上回归证明交付物确实运行。
