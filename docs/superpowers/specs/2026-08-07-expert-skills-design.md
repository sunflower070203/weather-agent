# 专家技能设计（Skill=专家身份）

## 第一性原则取舍

户外决策场景的真实需求是“谁能以专家身份说清楚这一段”：天气怎么说、风险怎么判、装备怎么备。技能在本文档中定义为 **人设 + 知识挂载 + 输出职责** 的确定性单元，而不是 LLM 自由工具调用。

## 结构

- 注册表：`weather_agent/experts.py` 中 `Expert(id, name, description, should_render, render)`，顺序即输出顺序；
- 上下文：`ExpertContext`（活动计划、地点、预报、时段点、风险结果、知识库）；
- 触发：`should_render` 确定性谓词；装备顾问仅在知识库存在匹配条目时出场；
- 渲染：每位专家只输出自己负责的段落，段标题即专家名；
- 声明式定义：`skills/<id>/SKILL.md` 记录角色、触发、输入、输出契约与实现位置，供人阅读与未来 LLM/MCP 迁移。

## 三位专家

| 技能 | 职责 | 知识来源 |
|---|---|---|
| `weather-interpreter`（气象顾问） | 时段概况、通俗解读、决策依据（含风险峰值） | 预报数据与风险规则，不引用语料 |
| `outdoor-safety`（户外安全顾问） | 结论、方案一/方案二、偏好提示 | 风险规则与 `planning.py` 替代时段 |
| `gear-advisor`（装备与补给顾问） | 装备/补给/穿着建议 | `data/outdoor-advice.json` 中 `expert="gear-advisor"` 条目 |

## 检索

`KnowledgeBase.advice_for(activity, topics, expert=...)`：在既有活动与主题打分基础上增加专家过滤；装备顾问无匹配条目不输出段落，避免空标题。

## 评估

- 单元测试：注册表顺序、专家元信息、触发谓词、各段渲染契约、知识引用；
- Agent 集成：雨日与晴日推荐均包含三位专家段落；
- 评估场景：`agent.028`（雨日三位专家分工）、`agent.029`（晴日仍三位专家分工），全部离线确定性运行。

## 局限

语料为人工整理的通用建议，不替代官方预警和现场判断；专家选择由规则驱动，未引入模型自主选角。未来若切换为 LLM 工具调用架构，`skills/<id>/SKILL.md` 可作为技能描述直接挂载，三位专家映射为三个工具。
