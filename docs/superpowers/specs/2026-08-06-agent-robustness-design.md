# Agent 鲁棒性第一阶段设计

日期：2026-08-06

## 目标

在不增加第三方 API、RAG、Memory 或多 Agent 的前提下，提高当前户外天气 Agent 对口语输入、歧义选择、用户纠错和外部服务失败的处理稳定性。

本阶段完成标准：20 条固定对抗测试全部通过，且现有自动化测试零回归。

## 范围

本阶段包含：

1. 建立覆盖真实对话失败模式的 20 条对抗测试。
2. 强化地点候选状态下的自然语言选择、取消和改写行为。
3. 保证模型解析失败不会污染已确认的活动计划。
4. 将错误回复改为包含明确下一步操作的可恢复提示。
5. 在最终建议中提供简短、可核验的决策轨迹。

本阶段不包含：

- 第三方模型或天气 API。
- RAG、长期 Memory、Skill 或 MCP。
- 多 Agent、规划—执行—反思循环。
- 自动重试框架或大规模架构重构。
- 展示模型隐藏推理过程。

## 设计原则

- 确定性操作由代码处理，开放式语义理解交给模型。
- 在当前对话状态能够解释输入时，不进行不必要的模型调用。
- 状态更新必须具备原子性：完整更新成功前保留旧计划。
- 错误信息必须说明发生了什么以及用户下一步可以做什么。
- 每项新增行为都必须先有失败测试，再写最少实现代码。

## 对抗测试矩阵

20 条固定用例分为五组，每组四条：

### A. 口语与省略

1. 一句话包含活动、地点、相对时间和时长。
2. 多轮逐项补齐缺失信息。
3. 使用“一晚”“半天”等口语时长。
4. 使用“这周六早上”等相对时间。

该组主要验证发送给模型的上下文约束和结构化更新结果，不用脆弱的关键字规则重复实现自然语言理解。

### B. 地点候选交互

5. 使用纯数字选择候选地点。
6. 使用“第二个”选择候选地点。
7. 使用候选名称中的唯一文本选择地点，例如“选北京那个”。
8. 使用“都不是”退出候选状态并请求更具体的地点。

候选文本选择只在唯一匹配时成功；零匹配或多匹配时继续展示候选并提示可用回复方式。

### C. 纠错与计划修改

9. 候选状态下输入新的地点，退出旧候选并重新解析。
10. 修改已填写的活动时间。
11. 修改已填写的地点。
12. 使用“重新开始”清空当前计划和候选状态。

“重新开始”作为 Agent 层命令处理，使聊天输入与界面重置按钮行为一致。

### D. 非法与对抗输入

13. 候选序号为 0。
14. 候选序号超出范围。
15. 空白或仅标点输入不改变计划。
16. 输入要求忽略系统规则或生成非 JSON 内容时，不接受越权字段。

现有界面仍负责空白消息的第一道拦截；Agent 层增加保护，避免其他调用入口绕过界面。

### E. 依赖失败与安全降级

17. 模型输出不是对象或字段值无效时保留旧计划。
18. 地理编码失败时保留计划并提示重试或改写地点。
19. 天气服务失败时不生成适宜性结论，并提示重试。
20. 活动时间不在预报范围时说明限制并建议可执行的时间调整。

## 组件与数据流

### `ActivityExtractor`

- 继续通过 `complete_json(messages)` 获取结构化更新。
- 验证返回值必须是字典，只接受允许字段。
- 在 `ActivityPlan.with_updates()` 完整成功后才返回新计划。
- 任何模型格式或字段验证失败统一转换为 `ActivityExtractionError`。

### `WeatherAgent`

消息处理顺序固定为：

1. 识别全局重置命令。
2. 如果存在地点候选，尝试确定性解释选择、取消或地点改写。
3. 对普通消息调用 `ActivityExtractor` 更新计划。
4. 信息不足时只追问下一个必要字段。
5. 信息完整后依次执行地理编码、天气获取、风险评估。

候选选择解析只支持本阶段测试明确要求的三种形式：数字、中文序数词、候选名称唯一片段。不会引入通用自然语言命令框架。

### `AgentResult`

保持现有返回结构。决策轨迹作为面向用户的简短文本加入推荐消息，包含：

- 已采用的活动计划。
- 解析到的地点及是否为城市级近似。
- 天气数据起报时间和评估时段。
- 命中的公开风险规则。

该轨迹是输入、工具结果和规则的摘要，不包含模型隐藏思维链。

### UI

- 保持现有 Gradio 布局和状态对象。
- 更新使用提示，展示自然语言地点选择、退出候选和重新开始的示例。
- 对可恢复错误保留聊天历史与计划摘要。

## 状态与错误处理

- 模型解析失败：计划与候选状态保持不变，提示用户换一种说法或补充活动、地点、时间、时长。
- 候选选择失败：候选状态保持不变，重新展示候选和支持的回复方式。
- 用户否定全部候选：清除候选状态，保留其他计划字段，清除地点字段并要求输入更具体地点。
- 候选状态下输入新地点：清除旧候选，将该消息作为新的计划更新处理。
- 地理编码或天气服务失败：不清除已收集计划，允许用户原消息重试。
- 重置命令：清除计划和候选状态，返回确认消息。

## 测试策略

- 对确定性状态机使用单元测试，不调用真实网络。
- 对模型提示和结构化验证使用可记录消息的假模型。
- 对地理编码和天气失败使用现有依赖注入假对象。
- 20 条对抗测试以行为断言为主，不断言实现细节或完整文案。
- 每个实现步骤遵循红—绿—重构：先运行新增测试并确认因缺少行为而失败，再写最少代码使其通过。
- 完成时运行完整 `unittest` 测试套件。

## 实施顺序

1. 先补齐 `ActivityExtractor` 的返回类型、非法更新和状态原子性测试。
2. 实现地点候选的数字、中文序数词、唯一文本、全部否定和地点改写。
3. 实现 Agent 层空白与重置命令。
4. 改进可恢复错误提示和决策轨迹。
5. 补齐对抗矩阵至 20 条并运行完整回归测试。
6. 将验证结果和当前限制同步到 README。

## 已知限制

- 相对时间和复杂口语仍依赖模型能力，测试只能约束项目传递的上下文与接收的结构化结果，无法保证远端模型永不波动。
- 中文地点名称可能存在同名或模糊片段，只有唯一匹配才会自动确认。
- 本阶段不实现持久化会话；页面刷新后状态仍会丢失。
- 外部天气和地理编码服务不可用时，Agent 只能安全降级，不能产生新的可信气象结论。
