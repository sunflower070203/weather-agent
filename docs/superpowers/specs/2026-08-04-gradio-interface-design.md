# 户外天气决策 Agent：Gradio 界面设计

## 目标

在不改变现有决策内核的前提下，为比赛作品增加可公开访问的中文对话界面。用户应能从空白会话开始，经过信息补全、地点确认、天气查询和风险评估，得到带数据依据的两套行动方案。

成功标准：

- 浏览器中可以完成一条端到端对话；
- 不同浏览器会话之间不共享 `ActivityPlan` 或地点候选；
- 用户可以一键清空当前会话并重新开始；
- 页面不显示 API 密钥、完整请求 URL或内部异常堆栈；
- 缺少环境变量时，页面显示可理解的配置错误；
- 可由 ModelScope 创空间使用 `python app.py` 启动。

## 已选方案与取舍

采用单页 Gradio `Blocks`：左侧为主要聊天区，右侧为计划摘要和使用说明，底部提供输入框、发送按钮及重新开始按钮。

没有选择仅使用 `ChatInterface`，因为它难以清楚展示当前结构化计划和数据依据；没有选择自建前端与 API 服务，因为会增加部署、跨域和状态同步风险。`Blocks` 在交付速度、展示能力和维护成本之间更合适。

## 信息架构与视觉方向

视觉采用“户外观测记录”风格：深墨绿、雾白和警示橙作为主色，细网格与数据标签强化气象工具感。避免复杂动画和大型图片，保证创空间加载速度。

页面内容：

1. 标题区：产品名称、用途和“数据驱动，不替代官方预警”提示；
2. 聊天区：显示用户输入、主动追问、地点选项和最终建议；
3. 计划摘要：活动类型、地点、开始时间、持续时间、参与者和风险偏好；
4. 示例区：提供骑行、徒步、露营三条可点击输入；
5. 操作区：发送与重新开始；
6. 页脚：天气数据来源、城市级近似定位说明和免责声明。

移动端降级为单列布局，聊天区优先，计划摘要位于聊天区下方。

## 组件与状态边界

`app.py` 只负责组装依赖和启动 Gradio，不保存全局会话状态。

新增 `weather_agent/ui.py`：

- `create_agent()`：从环境变量创建一套新的 `WeatherAgent` 依赖；
- `new_session()`：为每个 Gradio 会话创建独立 Agent；
- `respond(message, history, agent)`：调用 `handle_message`，追加聊天记录并返回计划摘要；
- `reset_session()`：清空聊天记录并创建新的 Agent；
- `build_app()`：声明 Gradio 组件、事件绑定和样式。

每个浏览器会话通过 `gr.State` 持有独立 `WeatherAgent`。禁止把可变 Agent 实例定义为模块级单例。

## 数据流

```text
浏览器输入
  -> Gradio respond
  -> 当前会话的 WeatherAgent.handle_message
  -> ModelScope 参数提取
  -> 缺字段：返回下一问题
  -> 地点歧义：返回编号候选
  -> 天机天气：获取逐小时预报
  -> 确定性风险规则
  -> 聊天回复 + 结构化计划摘要
```

“重新开始”会同时替换 `gr.State` 中的 Agent、清空聊天记录和恢复空计划摘要。

## 错误处理

- 空输入不调用模型，保留历史并提示用户输入活动计划；
- ModelScope、地理编码或天气服务失败时，显示领域层安全文案；
- 缺少环境变量时，应用仍能打开，在首次交互时提示缺少的变量名；
- 地点没有结果时要求补充城市或行政区；
- 活动日期超出预报范围时不生成适宜性结论；
- 服务器日志不记录 Token、天气 API Key 或含密钥的 URL。

## 测试与验收

先测试不依赖浏览器渲染的 UI 适配层：

- 空输入不会调用 Agent；
- 一轮消息正确追加历史并更新计划摘要；
- 两个会话使用不同 Agent 实例；
- 重置后状态和聊天记录清空；
- 初始化缺少密钥时返回安全配置提示。

然后执行：

1. 全部 Python 单元与场景测试；
2. 本机启动 `app.py` 并检查首页加载；
3. 浏览器完成骑行示例端到端对话；
4. 检查移动宽度布局；
5. 部署到 ModelScope 后从无痕会话重新执行演示流程。

## 明确不做

- 用户账号、数据库和长期记忆；
- 地图、路线规划与精确 POI 坐标；
- 语音、图片生成和复杂动画；
- 多 Agent 编排；
- 管理后台和调用量统计。

这些功能不会提升当前核心闭环的完成度，且会增加 2026-08-10 前的交付风险。
