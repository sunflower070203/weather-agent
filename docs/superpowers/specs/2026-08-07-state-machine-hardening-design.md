# Agent 状态机加固二期设计

## 背景与目标

2026-08-06 的 30 条 ModelScope 线上黑盒测试证明核心 Agent 闭环可运行，同时暴露四个确定问题：重置后的状态可能残留；地点候选阶段会阻塞普通修改；过去时间和异常时长未在调用地理编码前拒绝；常见城市产生不必要的同名候选确认。

本阶段只修复这些已复现问题。成功标准是新增回归测试先在当前代码失败、最小修复后全部通过，并保持现有 50 项测试不回归。不加入 RAG、Skill、Memory、多 Agent 或新框架。

## 方案选择

采用现有 `WeatherAgent` 的局部状态机加固：在既有消息入口增加确定性命令优先级与计划边界校验，并在地理编码结果层做保守排序/去重。

不采用以下方案：

- 重写为通用意图路由器：改动面大，距离提交截止时间过近。
- 引入 LangGraph 或多 Agent：不能直接解决已复现的状态和校验顺序问题，会增加部署风险。

## 行为设计

### 1. 重置一致性

`WeatherAgent` 的重置命令必须同时清空 `plan` 和 `pending_locations`。Gradio 的重置适配必须同时返回空聊天历史、空 Agent 状态和空计划摘要。新增组合测试模拟“已有计划与候选 → 点击重置 → 下一条消息创建全新 Agent”，防止只测试单个函数却遗漏事件输出映射。

若组合测试已通过，则不改生产 UI；把线上异常记录为需要重新部署后复测的平台/事件问题，避免无证据修改。

### 2. 候选阶段的命令优先级

优先级固定为：重置/清空 → 否定全部候选 → 有效候选选择 → 明确计划修改 → 重显候选。

“改成露营”“改成下午两点”“时长改为两小时”等明确修改应清除旧候选，并重新进入现有结构化提取流程。无法明确判断为修改的普通文本继续重显候选，避免把闲聊误当成地点。

### 3. 计划边界校验顺序

计划信息齐全后、调用地理编码前执行确定性校验：

- `start_time < now`：拒绝过去时间并要求提供未来时间。
- `duration_hours > 168`：拒绝超过 7 天的活动时长并要求缩短。
- 非正时长继续由 `ActivityPlan` 现有验证拒绝。

校验失败不得调用地理编码或天气服务，且保留其他已收集字段，方便用户只修改错误字段。

### 4. 常见城市消歧

地理编码结果先做精确名称与行政区匹配排序。对于北京、上海、天津、重庆四个直辖市，当查询是完整市名或不带“市”的标准名称，若存在同名且行政区一致的候选，则只返回该候选。其他城市只排序，不擅自丢弃候选。

该规则保持保守：不引入人口数据库，不猜测 POI，不自动选择普通同名县镇。

## 文件边界

- `weather_agent/agent.py`：候选阶段修改识别、计划边界校验。
- `weather_agent/geocoding.py`：直辖市精确匹配与候选排序。
- `tests/test_agent.py`：候选中断、过去时间、超长时长测试。
- `tests/test_geocoding.py`：常见城市排序/收敛测试。
- `tests/test_ui.py`：完整重置生命周期测试。
- `README.md`：验证结果、行为边界和线上复测记录。

## 测试策略

严格执行红—绿—重构：每项行为先写失败测试并单独确认失败原因，再写最少生产代码。最后运行：

```powershell
python -m unittest discover -s tests -v
python -m compileall -q weather_agent tests app.py
git diff --check
```

完成本地测试后部署至 ModelScope，并复跑针对四个缺陷的线上短回归；只有线上状态也符合预期才宣称修复完成。

## 明确不做

- 不修改风险阈值和天气建议文案。
- 不更换模型、天气 API 或地理编码供应商。
- 不重构 Gradio 布局。
- 不扩展骑行、徒步、露营之外的活动类型。
