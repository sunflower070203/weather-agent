# 户外天气决策 Agent

> 面向“天气智能创造营”生活服务赛道的学习型参赛项目。  
> 提交日期：2026-08-10  
> 当前原则：技术闭环 > 完成风险 > 产品丰富度

## 1. 第一性原则：我们究竟要完成什么

天气数据本身不是产品，聊天界面也不是 Agent。

本项目要解决的核心问题是：

> 当用户计划骑行、徒步或露营时，如何把天气数据转化为可靠、可解释、可调整的行动决策？

因此，系统必须完成以下闭环：

```text
理解用户目标
  -> 发现缺失条件并主动追问
  -> 保存结构化活动状态
  -> 选择并调用天气工具
  -> 使用确定性规则识别风险
  -> 生成可执行的备选方案
  -> 解释建议所依据的数据
  -> 接受用户修改并重新评估
  -> 在工具失败时安全降级
```

如果系统只完成“输入城市 -> 查询天气 -> 大模型生成一段建议”，则项目失败，因为那只是 API 包装的问答网站。

## 2. 项目目标

### 2.1 产品目标

用户通过多轮对话描述一次户外活动。Agent 主动补全关键信息，获取真实天气数据，识别风险，并给出“按计划举行、调整时间、调整地点或取消”等可执行方案。

### 2.2 学习目标

通过本项目掌握并记录一套可复用的 Agent 开发流程：

1. 场景与任务边界定义；
2. Agent 状态建模；
3. 大模型结构化输出；
4. 工具设计与调用；
5. 确定性规则与大模型协作；
6. 多轮状态更新；
7. 异常处理与安全降级；
8. Agent 测试与评测；
9. 部署、日志和复盘。

### 2.3 交付目标

在 2026-08-10 前交付：

- 可公开访问的 ModelScope 创空间；
- 可运行的户外天气决策 Agent；
- 可复现的核心测试案例；
- 清晰的项目说明、架构和演示流程；
- 一份基于真实开发过程整理的 Agent 开发复盘。

## 3. MVP 范围

### 3.1 必须完成

- [ ] 支持骑行、徒步、露营三类活动；
- [ ] 支持单个地点和未来天气预报；
- [ ] 主动询问缺失的活动信息；
- [ ] 使用结构化对象保存当前活动计划；
- [ ] 调用真实天气 API，而不是让模型编造天气；
- [ ] 判断降雨、高温、低温和大风风险；
- [ ] 输出至少两个可执行方案及其依据；
- [ ] 用户修改时间或地点后重新查询并评估；
- [ ] 清楚展示天气数据的地点、时间、单位和更新时间；
- [ ] 正确处理 API 超时、空数据、地点歧义和预报范围外日期；
- [ ] 提供固定测试集和测试结果；
- [ ] 在 ModelScope 创空间完成部署。

### 3.2 明确不做

以下内容除非核心闭环已经通过测试且仍有充足时间，否则不得加入：

- 多 Agent 协作；
- RAG 或知识库；
- 用户账号和数据库；
- 长期记忆；
- 地图和路线规划；
- 自动定时提醒；
- 语音交互；
- 图片或视频生成；
- 气象模型训练或微调；
- 通用旅行规划；
- 与核心闭环无关的复杂前端效果。

## 4. 成功标准

只有同时满足以下条件，项目才算完成：

### 4.1 功能成功

给定“周六想在北京组织一次骑行”等不完整输入，Agent 能够：

1. 识别缺失字段；
2. 通过多轮对话补齐条件；
3. 调用正确工具并传入正确参数；
4. 根据返回数据稳定判断风险；
5. 给出可执行建议及依据；
6. 在用户修改计划后更新状态和结论。

### 4.2 可靠性成功

- 天气工具失败时，Agent 明确说明无法完成评估；
- Agent 不得补写工具没有返回的数据；
- 相同天气指标应得到稳定的风险等级；
- 每条关键建议都能追溯到数据、规则或明确假设；
- 日期超出预报范围时不得伪装成有效预报。

### 4.3 工程成功

- 核心状态、工具和风险规则可以独立测试；
- API 密钥只通过环境变量配置；
- 日志能够还原模型调用、工具调用、状态变化和错误；
- 新开发者阅读本文档后能够运行、测试和修改项目；
- ModelScope 公开链接可以从空白会话完成核心演示。

### 4.4 学习成功

项目完成后，开发者能够脱离当前代码解释：

- Agent 与普通问答程序的区别；
- 状态如何在多轮对话中流转；
- 模型在什么情况下调用什么工具；
- 为什么风险判断不能完全交给大模型；
- 如何测试 Agent，而不只测试页面能否打开；
- 如何把本项目的方法迁移到另一个 Agent 场景。

## 5. 初始技术方案

为降低一周内的交付风险，采用最少依赖的单 Agent 架构：

- Python：主要开发语言；
- Gradio：演示界面及 ModelScope 创空间入口；
- Pydantic：活动状态、工具参数和模型输出校验；
- HTTP 客户端：调用天气 API 和大模型 API；
- 普通 Python 函数：实现可测试的风险规则；
- unittest：单元测试和场景测试。

当前不引入 LangGraph、AutoGen 等 Agent 编排框架。只有手写状态循环无法满足已确认需求时，才重新评估是否引入。

### 5.1 计划状态

初始状态至少包含：

```text
ActivityPlan
- activity_type      活动类型
- location           活动地点
- start_time         开始时间
- duration           持续时间
- participants       参与人群或特殊情况
- risk_preference    风险偏好
- weather_snapshot   本次使用的天气快照
- identified_risks   已识别风险
- recommendation     当前建议
- status             信息收集、已评估或已确认
```

### 5.2 已确认的天气 API

当前选用“全球范围10天基础要素包（60分钟间隔）”：

- 请求方式：`GET https://api.tjweather.com/v2`；
- 查询范围：全球单点经纬度；
- 时间分辨率：1小时；
- 预报时效：最长10天；
- 更新频率：每日2次；
- 返回格式：JSON；
- 试用额度：1000次，QPS 5次/秒；
- 有效期：2026-08-03 至 2026-09-02；
- 鉴权参数：`key` 与 `subscriptionId`；
- 密钥环境变量：`TJWEATHER_API_KEY`；
- 订阅标识环境变量：`TJWEATHER_SUBSCRIPTION_ID`。

支持要素：

| 编码 | 含义 | 单位 | MVP用途 |
|---|---|---|---|
| `wd10m` | 10米风向 | ° | 风向说明 |
| `ws10m` | 10米风速 | m/s | 大风风险 |
| `t2m` | 2米温度 | °C | 高温、低温风险 |
| `rh2m` | 2米相对湿度 | % | 体感和辅助说明 |
| `psz` | 地表气压 | Pa | 保留，不直接作为首版风险规则 |
| `tp` | 降水 | mm/hr | 降雨风险 |

默认请求字段为 `wd10m,ws10m,t2m,rh2m,psz,tp`。接口返回 `code`、`message` 和 `data`；`data` 中包含单位、逐时要素数据及起报时间。

已实测时间分辨率参数：`t_res=1h` 返回业务码 `200`、240个逐小时数据点，相邻时间间隔60分钟；`t_res=60min` 返回 HTTP 403。项目统一使用 `1h`，不得照抄官网 Python 示例中的 `60min`。

### 5.3 模型与程序的职责边界

大模型负责：

- 理解自然语言；
- 提取和更新活动信息；
- 判断还需要询问什么；
- 比较方案；
- 生成自然、清晰的解释。

确定性程序负责：

- 参数验证；
- 天气 API 请求；
- 单位和时间处理；
- 风险阈值计算；
- 状态持久化；
- 错误分类；
- 日志和测试断言。

原则：能通过明确规则计算的内容，不交给大模型猜测。

- [ ] 一次性提供完整活动信息；
- [ ] 信息缺失，需要多轮追问；
- [ ] 地名存在歧义；
- [ ] 正常、适宜的天气；
- [ ] 单项降雨风险；
- [ ] 单项高温、低温或大风风险；
- [ ] 多项风险同时存在；
- [ ] 查询日期超出预报范围；
- [ ] 天气 API 超时；
- [ ] 天气 API 返回空值或异常结构；
- [ ] 用户中途修改日期；
- [ ] 用户中途修改地点；
- [ ] 用户要求忽略明显风险；
- [ ] 模型是否引用不存在的天气数据；
- [ ] 新会话是否会错误继承上一会话状态。

评测维度：

1. 工具选择是否正确；
2. 工具参数是否正确；
3. 状态更新是否正确；
4. 风险判断是否符合规则；
5. 是否出现数据编造；
6. 建议是否具体、可执行；
7. 异常情况下是否安全降级。

固定20项对抗矩阵：

1. 信息不足时只追问下一字段且不调用工具；
2. 多地点候选必须由用户确认；
3. 纯数字地点选择；
4. “第二个”等中文序数词选择；
5. “选北京那个”等唯一名称片段选择；
6. 0、越界数字和无效序数不改变候选状态；
7. “都不是”只清除地点；
8. 候选状态下改写地点会重新进入提取与查询；
9. 仅标点输入不调用模型；
10. 对话内“重新开始”清除计划和候选；
11. 地理编码失败保留计划并提示重试；
12. 天气服务失败不生成适宜性结论；
13. 活动时间超出预报范围时建议调整时间；
14. 城市级近似坐标必须明确标注；
15. 无风险建议显示公开决策依据；
16. 有风险建议显示命中的规则、等级、数值和单位；
17. 模型非 JSON 对象返回被拒绝且旧计划不变；
18. 非法活动类型被领域校验拒绝；
19. 提示注入产生的越权字段被白名单丢弃；
20. 模型解析失败在 UI 中保留计划摘要并提示换一种说法。

## 12. 本地运行与部署

### 12.1 本地运行

在项目根目录的 PowerShell 中执行：

```powershell
py -m pip install -r requirements.txt
py -m unittest discover -s tests -v
py app.py
```

然后访问 `http://127.0.0.1:7860`。应用默认监听 `0.0.0.0:7860`，便于容器和 ModelScope 创空间访问。

### 12.2 必需环境变量

只配置变量值，不要把实际密钥写入仓库：

- `MODELSCOPE_ACCESS_TOKEN`
- `TJWEATHER_API_KEY`
- `TJWEATHER_SUBSCRIPTION_ID`

### 12.3 ModelScope 创空间

目标空间：<https://modelscope.cn/studios/sunh0203/outdoor-weather-agent>

需要同步 `app.py`、`requirements.txt`、`weather_agent/`、`README.md` 和许可证文件（如平台要求），然后在创空间的环境变量或密钥设置中配置上述三个变量。启动入口为 `python app.py`。部署后必须用一个新会话重新执行骑行示例，确认会话状态不会沿用本地或其他访客的数据。
